04 / Recovery model

Crashes become retries

Each boundary has a durable checkpoint, so a process crash does not silently lose the requested workflow.

CASE A

Crash before DB commit

The transaction rolls back. The upload service removes the new MinIO object.

CASE B

Crash before Redis enqueue

The pending outbox row survives. A restarted dispatcher claims it later.

CASE C

Crash after Redis enqueue

Lease expiry replays the outbox event; stable job IDs avoid duplicate jobs.

CASE D

Worker crashes while active

BullMQ detects a stalled lock and makes the job available for processing again.

CASE E

Recording is replaced

The worker must verify active domain state before writing any stale result.

CASE F

Provider fails temporarily

BullMQ retries three times with exponential backoff before final failure.

06 / Glossary

Do not mix these concepts

Domain event

A past-tense fact such as recording.uploaded.

BullMQ job

A command such as transcribe-recording.

Outbox

A durable bridge between a PostgreSQL commit and Redis delivery.

Analysis run

The durable business record for one transcript-analysis attempt.
